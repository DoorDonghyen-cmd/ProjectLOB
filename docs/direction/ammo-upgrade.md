# 탄환 강화 통합

2026-11-06 · 사용자 확정 방향을 본편 정비소에 연결했다. [실제 화면·입력/저장·밸런스 비교](../qa/reports/ammo_upgrade_single_2026-11-06/README.md). 수치의 최종 균형과 사람의 선택 이해도는 확인 전이다.

## 사용자 확정 — 영구 강화 한 가지로 통합

- 사용자는 별도 방열 개조를 제거하고 화력/압축도 나누지 않는 방향을 승인했다. 정비소의 영구 성장은 **탄환 강화 하나**이며 같은 성능의 탄2발을 강화 탄1발로 만든다. 압축은 이 작업의 제작 방식/연출에 흡수한다.
- 공격탄은 피해, 특수탄은 고유 효과를 중심으로 결과를 비교한다. 새 선택에 별도의1발→1발 화력/방열 개조를 두지 않는다. 기존 개조 ID/보유 탄은 저장 호환 대상으로 보존한다.
- 전투 중 임시 압축은 현재 탄창의 전술 선택이므로 영구 성장과 구분한다. 이번 승인으로 임시 탄의 사용/복원 규칙을 바꾸지 않는다.
- 강화 대가2→1과 최종 수치의 적절성은 별도 밸런스 검증이 필요하다. [개발자 원문/설계 이론/도구 조사와 적용 방법](../history/research/balance-methods-2026-11-06.md)을 먼저 정리했다. 레어·에픽의 수치/출현률/상위 합성식은 확정하지 않았다.
- **본편 구현:** 정비소4탭·단일 비교 창·현재 소유/방문 재확인·취소/확정·자동 저장/재개를 연결했다. 현대 장소의 별도1발→1발 개조 명령은 거절하며 과거 보유 개조 탄과 구형 유료 상점 명령을 보존한다. 이전3방식236검사는 과거 시안의 기록이다.

## 목적과 판단

사용자는 기본탄 강화와 압축의 통합, 직관적인 이름, 별도 비교 창, 등급에 따른 카드 외형을 요청했다. 확인할 질문은 **원본2발을 강화1발로 바꿀지, 유지하거나 다른 정비를 할지 결과와 비용을 보고 고를 수 있는가**다.

본편은 ‘탄환 강화’ 한 탭을 사용한다. 과거 기본/철갑/연타의 화력·방열 개조 ID는 저장 호환을 위해 유지한다. 옛 `shop_refine()`은 거절되는 은퇴 명령이며 이를 되살려 별도 기본탄 강화 경로를 만들지 않는다.

기본 조작은 실제 Campaign/대표 픽스처와5화면 크기로 확인했다. 밸런스는5총기·시드17/운반복과 추가 리액터·시드731042/정찰복의 실제 획득 경로에서11정비 상태를 비교했다. 소이탄 화면은 그 실제 획득 상태를 불러 확인했다. 작업대 장면·기존 하단 탄 항목 크기·수치·저장 형식은 유지한다.

## 본편 통합 흐름

1. ‘탄환 강화’에서 대상 탄을 고른다. 다른 강화 방식 선택 단계는 두지 않는다.
2. 동일 성능의 재료2발과 결과1발을 나란히 비교한다. 발당 수치뿐 아니라 원본 두 발의 합계·발사 횟수/파츠 조건·탄약1발 감소의 대가를 읽을 수 있게 한다.
3. 강화 확정에서만 실제 Campaign 명령을 실행한다. 취소/대상 변경은 정비를 소비하지 않는다. 최소 보유량과 같은 성능2발 제한을 다시 확인한다.
4. 공격/지원 역할, 총기/파츠, 적 구성과 이후 전투 자원에 따라 강화와 유지의 가치가 달라지는지 검증한다. 평균 피해 증가만으로 통과시키지 않는다.

## 앞선3방식 시안 — 구현 기록

아래는 [이전236검사 시안](../qa/reports/ammo_upgrade_2026-11-06/README.md)의 이력이다. 현재 실행물과 새 규칙의 원본으로 사용하지 않는다.

1. 정비소의 **탄환 강화**에서 보유 탄을 선택한다. 기존 압축/개조 두 진입을 하나로 묶는다.
2. ‘강화 상세’로 전용 창을 연다. **압축 강화 / 화력 개조 / 방열 개조**를 같은 위치에서 비교한다. 창 안에서도 강화할 탄환을 바꿀 수 있다.
3. 왼쪽 소모 탄과 수량, 오른쪽 결과 탄과 수량을 본다. 가운데는 **발당 대표 효과·발당 발열·발당 점유·전체 탄약**의 전후 값이다. 화상·경직 등의 효과/순서 제약도 실제 Readability에서 가져온다.
4. **강화 확정** 때만 실제 명령을 실행한다. 선택 변경/닫기/취소에는 비용이 없다. 정비1회는 다른 정비 작업과 경쟁한다.

압축의 두 재료는 **내부 ID까지 같은 성능의 탄2발**이다. 서로 구별되지 않는 동일 사본을 두 번 클릭하게 하지 않고 대상 선택 시 두 발을 함께 제시한다. 서로 다른 위력/개조의 탄을 섞는 새 합성식은 이번에 도입하지 않는다.

| 당시 방식 | 소모/결과 | 당시 제약과 대가 | 명령 |
|---|---|---|---|
| 압축 강화 | 같은 탄2발 → 압축1발 | 최소 보유량 유지, 탄에 따른 발열/점유/순서 변화, 재압축 불가 | `Campaign.resolve("compress", id)` |
| 화력 개조 | 선택한1발 → 화력 개조1발 | 프로필 탄만, 다른 사본 유지, 이미 개조한 탄은 불가 | `Campaign.tune(index, "power")` |
| 방열 개조 | 선택한1발 → 방열 개조1발 | 프로필 탄만, 발열 최저값/중복 개조 제한 | `Campaign.tune(index, "cool")` |

가짜 결과식을 UI에서 계산하지 않는다. 각 선택은 Campaign/Model을 깊게 복제해 실제 명령을 적용한 결과로 비교하며, 확정 직전에 현재 소유·방문 상태를 다시 확인한다. 정비소는 무료1회다. 구형 상점의18Cr 압축/12Cr 개조와 전투의 임시 압축은 각 비용/복구 규칙을 유지하며 이번 시안의 무료 정비와 혼합하지 않는다.

## 등급과 강화 상태

- 현재 실제 등급은 일반/고급이며 압축형과 고출력 증폭형이 고급이다. 기본탄의 위력 프로필·화력/방열 개조는 별도 정보다. 위력이 높거나 개조했다는 이유로 희귀도가 올라가지 않는다.
- 본편 `Content.grade()`의 기본탄 일반형은 보급 분류 -1이다. 통합 시안의 소모/결과 카드에서는 일반 외형으로 함께 보여 준다. 저장/가격/획득에 쓰이는 분류는 바꾸지 않았다.
- 일반은 회철색 단일 표식, 고급은 황동 이중 표식/하단 레일이다. 레어의 백납 보라·측면 레일/세 표식, 에픽의 구리색 모서리 보강/네 표식은 **후속 외형 제안**이다. 색을 빼도 표식 수와 틀 구조가 다르다. 등급 비교는 같은 관통탄 그림을 사용해 외형 변수만 비교한다.
- 레어/에픽의 효과·출현률·가격·상위 압축식은 미구현이며 사용자 확정 사항으로 기록하지 않는다. 시안에서는 기존 두 등급만 실제 결과에 연결한다. 전투 카드/다른 화면으로 일괄 적용하지 않았다.

## 검토 결과와 본편 조건

[본편 화면·기능/저장·밸런스 기록](../qa/reports/ammo_upgrade_single_2026-11-06/README.md). 전용 창은 에디터에서도 대표 구성이 보이는 `workbench/upgrade_dialog.tscn`과 작은 창 상속 씬이다. 신규UI2,015·기존 정비1,881·HUD11,558검사 실패0. 실제 사용자 저장과 분리된 QA 경로로 취소/확정/재확정·크기 변경/포커스·개조 보유 탄·저장/재개를 확인했다.

11정비 상태에서 유지/강화/가방 확장을 각각 공개 정보 정책2종과 미래 정보 탐색으로 비교했다. 같은 첫 조우에서 공개 운용의 통과를 만든 강화 사례와 반대로 실패한 사례가 모두 있다. 스파이크의 항상 강화 경로는 마지막 보스의 통과 경로를 탐색 범위 안에서 찾지 못했지만, 동일한 실제 정비 상태에서 원본을 유지한 분기는24행동/잔탄9발로 끝까지 통과하고 저장·재개도 통과했다. 자동 운용의 승패는 관측값이며 모든 강화 경로가 무조건 이겨야 하는 통과 조건을 두지 않는다. 쓴 탄은 다음 교전에서 복구되고 강화로 영구 보유량이1발 줄어드는 대가를 본다.

유지할 근거는 탄종과 기본탄을 같은 흐름에서 비교하고 ‘강화하지 않고 다른 정비’를 선택할 이유를 설명할 수 있는 것이다. 소모2발과 발당 성능을 혼동하거나 효과 설명의 스크롤/대상 탐색이 반복을 만들면 수정한다. 자동 기능 통과는 이 이해도/선호의 증거가 아니다.

본편 연결은 완료했다. 다음은 사람 플레이에서 강화의 체감/원본 유지 이유, 특히 증폭탄의 다음 탄창 강화와 마지막 발 제약이 읽히는지 확인하는 것이다. 같은 창에 구형 상점이나 관문의 별도 비용을 연결할 경우 각 진입의 허용 명령과 저장을 별도로 검증한다. Android 실기기, 사람의 선택 이해도, 레어·에픽 규칙은 미검증/미결정이다.
