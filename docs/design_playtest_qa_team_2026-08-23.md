# 전용 플레이 QA 팀 상세 기획

> 작성일: 2026-08-23
> 상태: Phase A~F 구현·전방 검증 완료
> 적용 범위: ProjectLoB 전용 에이전트 2명 + 기존 전투 시뮬레이터 1명

## 1. 목적

개발자가 기능을 구현한 뒤 사람이 매번 처음부터 전 구간을 확인하지 않아도,
동일 빌드를 서로 다른 관점에서 독립적으로 플레이하고 다음 세 종류의 증거를 남기는
전용 QA 팀을 구축한다.

1. 기능이 기획대로 동작하는가.
2. 플레이어가 화면에 공개된 정보만으로 규칙과 선택 결과를 이해할 수 있는가.
3. LIFO 장전 순서 설계와 거리 유지가 실제 플레이에서 반복 가능한 재미를 만드는가.

이 팀은 인간의 주관적 재미를 대체하지 않는다. 자동 플레이와 텔레메트리로
`지배 전략`, `무의미한 행동`, `선택 다양성`, `압박 구간`, `피드백 불명확`을 찾아
인간 플레이테스트가 확인할 가설의 범위를 줄인다.

## 2. 팀 구성과 책임 경계

### 2.1 `15-gameplay-qa-lead`

기능 QA와 최종 통합 보고를 담당한다.

- 최신 커밋, 테스트 범위, 허용된 기존 이슈를 기록한 테스트 차터를 만든다.
- 메인 화면 → 구역 선택 → 준비실 → 맵 → 전투 → 보상 → 상점 → 다음 구역의
  실제 진행 경로를 검증한다.
- 크래시, 진행 불가, 저장 손상, 기획과 다른 정산, UI 입력 오류를 재현한다.
- 경험 테스터와 전투 시뮬레이터의 원본 결과를 받은 뒤 중복을 제거하고 심각도를 확정한다.
- 확정 버그만 `05-bug-report` 형식으로 등록한다.
- 테스트 중 소스 코드를 수정하지 않는다. 원인 분석은 재현 보고가 끝난 뒤 개발 단계에서 한다.

### 2.2 `16-gameplay-experience-tester`

플레이어 관점의 블랙박스 재미·UX 검증을 담당한다.

- 소스 코드, 기존 버그 목록, 개발자가 의심한 문제를 보지 않고 시작한다.
- 플레이어에게 실제로 공개되는 정보와 최소 규칙 설명만 사용한다.
- 장전 순서가 결과를 바꾸는지, 실패 이유를 사후에 이해할 수 있는지 기록한다.
- 탄환·파츠·경로·보상 중 사실상 하나만 고르게 되는 지배 선택을 찾는다.
- 재미 문제를 버그로 단정하지 않고 `관찰`, `반복 신호`, `인간 확인 필요`로 구분한다.
- 테스트 중 코드와 수치를 수정하지 않는다.

플레이 성향은 별도 직원이 아니라 이 테스터가 실행하는 프로필로 둔다.

| 프로필 | 행동 원칙 | 검출 목표 |
|---|---|---|
| 초심자 | 카드의 큰 글자와 추천만 보고 선택 | 학습성, 가독성, 잘못 유도하는 UI |
| 공격형 | 즉시 피해와 빠른 처치를 우선 | 화력 지배, 과잉 피해, 안전거리 과잉 |
| 보수형 | 명중·관통·거리 안전을 우선 | 방어적 무한 안정화, 전투 장기화 |
| 실험형 | 이전에 덜 쓴 탄·파츠·경로를 우선 | 죽은 콘텐츠, 조합 성립 여부 |

### 2.3 기존 `12-combat-simulator`

수학적 오라클 역할을 유지한다.

- 동일 상태에서 최적 탄창 순서와 생존 가능 해법을 계산한다.
- 명중, 이진 관통, 피해, 넉백, 접촉 턴, 리로드 마진을 검증한다.
- 경험 테스터가 어렵다고 느낀 이유가 실제 해법 부재인지 정보 전달 실패인지 분리한다.
- 재미를 평가하거나 UI 문제의 심각도를 결정하지 않는다.

### 2.4 최종 판단권

- 기능 결함의 판정과 등록: `15-gameplay-qa-lead`
- 수학적 정합의 판정: `12-combat-simulator`
- 재미 방향이 코어 비전과 맞는지 판정: `09-creative-director`
- 수정 우선순위 결정: `00-project-manager`와 사용자

## 3. 독립성 규칙

여러 에이전트가 같은 결론을 복제하지 않도록 입력 정보를 분리한다.

| 대상 | 제공 정보 | 제공하지 않는 정보 |
|---|---|---|
| QA 리드 | 요구사항, GDD, 허용 이슈, 내부 오라클 상태 | 개발자가 추측한 원인 |
| 경험 테스터 | 플레이어 규칙, 실제 화면, 플레이어 공개 상태 | 소스, 버그 목록, 예상 결론, 숨겨진 상태 |
| 시뮬레이터 | 원시 스탯, 전투 상태, 공식, 행동 기록 | UX 테스터의 감상과 결론 |

각 테스터는 먼저 독립 보고서를 완료한다. 리드는 그 이후에만 두 보고서를 전달받는다.
한 에이전트가 역할 이름만 바꾸어 연속으로 세 보고서를 작성하는 방식은 사용하지 않는다.

## 4. 실제 플레이 연결 방식

### 4.1 현재 기반

현재 프로젝트에는 다음 기반이 이미 있다.

- `PlaytestLogger` JSON 스키마 v3: 런, 로드아웃, 전투, 탄환, 탄종, 파츠, 상점, QA 세션·게임플레이 seed 기록
- 실제 `CombatManager`를 사용하는 결정론 전투 테스트
- 메인 씬을 인스턴스화하는 UI 스모크 테스트
- 대표 적 편성과 보스전을 즉시 여는 개발자 테스트 진입점

부족한 부분은 에이전트가 상태를 읽고 다음 행동을 제출하는 통로와 재현 가능한 전체 런
난수 제어다.

### 4.2 QA 브리지

Godot 내부에 파일 기반 상태/행동 브리지를 둔다. OS 마우스 좌표 자동화보다 안정적이며,
실제 씬과 버튼의 의미 단위 동작을 그대로 사용할 수 있다.

1. 게임이 `qa_runtime/<session_id>/state_<step>.json`을 기록한다.
2. 테스터가 같은 단계 번호의 `action_<step>.json`을 제출한다.
3. 게임은 행동이 현재 화면에서 합법인지 확인한 뒤 실제 메서드 또는 버튼 신호를 실행한다.
4. 다음 상태, 액션 결과, 플레이테스트 로그, 필요 시 화면 캡처를 기록한다.
5. 단계 번호가 다르거나 허용 목록에 없는 행동은 거절하고 인프라 오류로 분리한다.

상태 파일은 두 종류로 분리한다.

- `player_view`: 화면, 공개된 적 스탯, 보이는 탄창 깊이, 카드 설명, 합법 행동만 포함
- `oracle_state`: 숨은 기믹 카운터·전체 탄창·정산값을 포함하며 QA 리드와 시뮬레이터만 사용

대표 행동 계약은 다음과 같다.

```json
{"step": 12, "action": "load", "bullet_id": "chain"}
{"step": 13, "action": "confirm_load"}
{"step": 14, "action": "fire", "target_slot": 0}
{"step": 15, "action": "reload"}
{"step": 16, "action": "choose_route", "node_id": 203}
{"step": 17, "action": "buy", "offer_slot": 1}
{"step": 18, "action": "skip_reward"}
```

### 4.3 UI 검증

브리지는 좌표 대신 안정적인 컨트롤 이름과 `pressed` 신호를 사용한다. 다음 체크포인트에서는
Viewport 이미지를 PNG로 저장하고 경험 테스터가 화면을 직접 판독한다.

- 첫 메인 화면과 개발자 테스트 창
- 구역 선택과 준비실
- 전투 첫 장전 상태
- 4체 편성 및 동거리 적 배치
- 탄환/파츠 카드 상세 설명
- 상점 최초 진열, 리롤 후 진열, 구매 완료 상태
- 전투 보상과 디브리핑

픽셀 위치와 터치 영역 자체는 별도 UI 계약 테스트로 검사한다. 이미지 생성 실패나 브리지
타임아웃은 게임 버그가 아니라 `QA 인프라 실패`로 보고한다.

### 4.4 재현 가능한 런

게임플레이 결과와 화면 연출의 난수 소비 순서가 서로 영향을 주지 않도록 다음 스트림을 분리했다.

- 게임플레이 RNG: 맵, 편성, 보상, 상점, 이벤트, 전투 전용 `RandomNumberGenerator`
- 연출 RNG: 흔들림, 지연, 파티클 전용 스트림
- QA 세션 manifest에 `gameplay_seed`, 커밋 해시, 프로필, 시작 세이브를 기록

Phase D 기준으로 실제 메인 씬 2구역을 46개 의미 행동으로 재생하고 매 행동 뒤 진행 저널과
전체 RNG 상태를 저장한다. 동일 seed 재실행은 행동열·진행 상태·게임플레이 스트림이 같아야 하며,
FX seed는 독립적으로 달라도 된다. 전투 수학 검증은 기존 고정 전투 QA 브리지와 시뮬레이터가 맡는다.

### 4.5 경험 보고서와 프로필 비교

프로필 행동 정책은 경험 테스터의 reference에 두고 게임 코드가 선택을 강제하지 않는다.
원본 보고서는 `player_view`, 선택 전 예상, 선택 이유, 포기한 대안, 실제 결과만 보존하며
`oracle_state`가 섞이면 거절한다.

통합기는 같은 commit·scenario·seed·시작 로드아웃의 `beginner`, `aggressive`,
`conservative`, `experimental` 보고서 한 개씩만 비교한다. 선택 집중도,
리로드·무효 행동, 최소 거리, 과잉 피해, 전술탄 미사용, 파츠·경로 중복률을
따로 제시하고 종합 점수는 만들지 않는다. 세 프로필 이상의 반복만 `strong_signal`이며,
촉감·피로도는 항상 `human_confirmation`으로 남긴다.

## 5. 실행 모드

### 5.1 빠른 스모크

호출 예: `QA 팀으로 이번 변경분 빠른 검증해 줘`

- QA 리드: 변경 기능과 인접 화면의 정상 진행
- 시뮬레이터: 관련 전투 계약과 전체 회귀
- 경험 테스터: UI나 플레이 경험 변경이 있을 때 대표 프로필 1개
- 목표: 개발 직후 수 분 내 치명적 회귀 검출

### 5.2 기능 집중 QA

호출 예: `상점과 조합탄 변경을 QA 팀으로 검증해 줘`

- 동일 빌드와 고정 시나리오를 세 역할에 독립 배포
- 경험 테스터는 초심자·실험형 최소 2개 프로필 수행
- 관련 화면 캡처와 전투/상점 JSON을 모두 보존
- 목표: 기능 정확성, 가독성, 수학적 해법을 한 보고서에서 교차 확인

### 5.3 재미 검증

호출 예: `재미 QA로 1~2구역 네 프로필을 돌려 줘`

- 네 프로필이 같은 시작 조건과 비교 가능한 시드 묶음을 사용
- 특정 선택을 강제하지 않고 각 프로필 원칙에 따라 결정
- 선택 분포와 전투 호흡을 비교하되 평균 점수 하나로 축약하지 않음
- 목표: 지배 전략과 죽은 선택지, 반복 피로, 코어 재미 약화 신호 탐색

### 5.4 릴리스 게이트

호출 예: `릴리스 후보 빌드를 QA 팀 전체 검증해 줘`

- 전체 회귀, 저장 격리, 대표 UI 캡처, 35층 연속 런, 보스 5전 확인
- PC 패키지와 모바일 패키지는 기기별 입력·해상도 결과를 분리
- `높음` 이슈가 미해결이면 실패하고, `보통` 이슈는 사용자 승인 없이는 통과시키지 않음

## 6. 재미 검증 루브릭

경험 테스터는 숫자 평점만 남기지 않고 각 항목에 행동 증거를 연결한다.

| 축 | 확인 질문 | 대표 지표 |
|---|---|---|
| 이해 | 다음 탄의 결과와 실패 이유를 화면만 보고 설명할 수 있는가 | 도움말 재확인, 잘못 예측한 격발 |
| 선택 | 서로 다른 이득을 가진 선택이 실제로 둘 이상 존재하는가 | 선택 집중도, 건너뛰기, 미구매 |
| 순서 | 같은 탄 조합도 LIFO 순서에 따라 결과가 의미 있게 달라지는가 | 재장전 계획 변경, 결산 성공/실패 |
| 압박 | 안전하지만 무의미하거나, 계산과 무관하게 즉사하지 않는가 | 최소 거리, 남은 행동 마진 |
| 호흡 | 판단 사이에 의미 없는 반복 입력이 과도하지 않은가 | 리로드 턴, 무효 발사, 반복 장전 |
| 피드백 | 효과가 발동한 이유와 결과가 한 번의 관찰로 읽히는가 | 로그·배지·연출 불일치 |
| 다양성 | 총기·탄환·파츠·경로가 프로필에 따라 달라지는가 | 프로필 간 선택 중복률 |

판정 신뢰도는 다음처럼 분리한다.

- `재현 확정`: 같은 상태와 행동에서 항상 재현되는 기능 결함
- `강한 신호`: 독립 테스터 둘 이상 또는 서로 다른 프로필 셋 이상에서 반복
- `가설`: 단일 런이나 단일 프로필에서만 관찰
- `인간 확인`: 촉감, 연출 속도, 피로도처럼 사람이 최종 확인해야 하는 항목

## 7. 리포트와 버그 처리

런타임 원본은 커밋하지 않고 격리한다.

```text
qa_runtime/<session_id>/
  manifest.json
  functional/
  experience/
  simulator/
  screenshots/
  raw_logs/
```

통합 결과만 다음 위치에 보존한다.

```text
docs/qa/reports/qa_<date>_<short_commit>_<scope>.md
```

통합 리포트는 반드시 다음 순서를 따른다.

1. 빌드와 범위
2. 통과/실패 요약
3. 신규 버그와 재현 절차
4. 재미·UX 신호와 행동 증거
5. 시뮬레이터의 수학적 대조
6. 기존 이슈와 중복 여부
7. 다음 개발 우선순위 제안

버그 중요도는 기존 트래커에 맞춘다.

- 높음: 크래시, 데이터 손실, 진행 불가, 코어 전투 규칙 위반
- 보통: 주요 기능 오동작, 반복되는 오입력, 의미 있는 선택을 무효화하는 UI
- 낮음: 우회 가능한 표기·정렬·연출 문제

재미 가설은 버그 번호를 발급하지 않는다. 독립 반복 또는 사용자 확인으로 설계 결함이
확정된 경우에만 태스크 트래커의 기획 일감으로 승격한다.

## 8. 실제 협업 절차

한 번의 QA 요청은 다음 순서로 실행한다.

1. 주 에이전트가 커밋 해시, 변경 파일, 테스트 모드, 허용 이슈로 manifest를 만든다.
2. 서로 독립된 작업 컨텍스트에서 QA 리드, 경험 테스터, 시뮬레이터를 동시에 시작한다.
3. 각 테스터는 배정된 읽기 범위만 사용하고 원본 보고서를 제출한다.
4. 주 에이전트가 원본을 QA 리드에게 전달해 중복 제거와 심각도 통합을 요청한다.
5. QA 리드가 확정 버그를 버그 템플릿으로 작성한다.
6. `09-creative-director`가 재미 가설의 코어 비전 정합만 판정한다.
7. `00-project-manager`가 수정 우선순위를 정하고 사용자에게 승인받는다.
8. 개발 담당자가 수정한다. 최초 테스터 중 해당 문제를 발견한 역할이 재검증한다.

동시 실행이 불가능한 환경에서는 같은 순서를 직렬로 수행하되, 앞선 테스터의 결론을
다음 테스터에게 전달하지 않는다.

## 9. 중단 조건과 안전장치

- 크래시·저장 손상·진행 불가가 나오면 해당 세션을 중단하고 즉시 보고한다.
- QA는 전용 APPDATA 또는 사용자 데이터 경로를 사용하며 실제 플레이 세이브를 읽거나 쓰지 않는다.
- 테스트 에이전트는 소스, GDD, 밸런스 값을 변경하지 않는다.
- 브리지의 불법 행동 거절을 게임 난이도나 UX 문제로 집계하지 않는다.
- 자동화가 통과해도 레이아웃 촉감과 재미 문제는 인간 확인 표기를 유지한다.
- 기존 Open 버그는 신규 발견 수에 포함하지 않고 재현 여부만 갱신한다.

## 10. 도입 완료 기준

- 두 신규 스킬이 프로젝트 범위 `.agents/skills`에 설치되고 유효성 검사를 통과한다.
- 한 문장 명령으로 세 역할이 독립 실행되고 통합 리포트가 생성된다.
- 고정 전투에서 상태 → 행동 → 다음 상태 왕복이 20단계 이상 성공한다.
- 실제 씬 흐름에서 메인 → 전투 → 보상 → 상점 체크포인트를 재생한다.
- 동일 manifest 재실행 시 게임플레이 결과가 동일하다.
- 의도적으로 삽입한 샘플 결함을 기능 QA가 버그로, 경험 QA가 체감 신호로 각각 구분한다.
- 기존 전체 회귀 테스트가 유지된다.
