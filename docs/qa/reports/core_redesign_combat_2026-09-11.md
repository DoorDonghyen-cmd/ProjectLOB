## FAIL-01 — 저장 후 시드 정밀도 손실로 이후 교전 패가 달라짐

우선순위: **보통 / P2**. 낮은 일반 시드에는 영향이 없지만, 현재 UI가 제한 없이 받는 유효 정수 시드에서 "같은 시드·저장 재개" 계약을 어긴다.

재현:

1. `Model.start("single", 9007199254740993)`으로 시작한다. UI 시드 입력도 `int(seed_input.text)`를 통해 이 정수를 받을 수 있다.
2. `save_run()`으로 QA 저장 파일을 쓴다.
3. 새 Model에서 `restore_run()`을 호출한다. 반환값은 `true`다.
4. 양쪽에 같은 다음 교전 인덱스를 지정하고 `begin_encounter()`로 새 교전 패를 만든다. 전투 승리 과정의 영향을 분리하기 위해 교전 시작만 비교한 진단 픽스처다.

| 항목 | 저장 전 | 복원 후 |
|---|---|---|
| 시드 | `9007199254740993` | `9007199254740992` |
| 다음 교전 공개 패 | `precise, charge, mark, pierce, bore` | `bore, charge, mark, push, pierce` |
| 이후 RNG 상태 | 원본 | 불일치 |

동일 파일 왕복을 독립적으로2번 수행해 같은 결과를 확인했다. 현재 교전의 `rng_state`는 문자열로 저장되어 보존되지만 `seed`는 JSON 숫자이고, Godot JSON 파싱의 부동소수점 표현에서 2^53 초과 정수의 하위 비트가 손실된다. 이후 `begin_encounter()`가 `seed + floor × 104729`로 RNG를 다시 만들면서 분기한다.

기대: 앱에서 허용하는 시드는 저장/재개 후에도 정확하게 같아야 하며, 같은 선택을 했을 때 후속 교전 패도 같아야 한다.

수정 방향: `rng_state`처럼 seed를 문자열로 보존하고 로딩 때 검증한 정수로 복원하거나, 앱 입력 범위를 정확히 보존되는 정수 구간으로 명시적으로 제한한다. 기존 숫자 저장과의 호환을 고려한다. 이 감사에서는 수정하지 않았다.

## FAIL-02 — 저장 복원이 용량·재고 제약을 검증하지 않아 5발 탄창 수용

우선순위: **보통 / P2**, 저장 방어 문제. 정상 UI 조작으로 이 상태를 만들 수 있다는 주장은 아니다.

재현:

1. 정상 burst 런 형태의 상태에서 QA 픽스처가 `plan=[basic,basic,basic,basic,basic]`, `supply=9`인 유효 JSON 저장을 작성한다.
2. 새 Model의 `restore_run()`은 이를 `true`로 수용한다.
3. `confirm()`도 `true`를 반환한다.
4. `capacity()`는4인데 실제 `magazine.size()`가5가 된다. 두 번 동일하다.

기대: 복원 데이터는 배열/탄종 이름뿐 아니라 탄창·계획 용량, 기본 보급 범위, 계획과 보유 재고, 전술 덱 보존 등 최소 상태 불변식에 맞아야 한다. 부적합 파일은 현재 정상 상태를 유지한 채 실패해야 한다.

원인: `restore_run()`은 필수 키·일부 enum·일부 배열의 탄종 이름만 확인한다. `confirm()`은 평소 `load_round()`가 만든 합법 계획이라고 믿으므로 복원된 과대 계획을 재검사하지 않는다. 일반적인 잘린 JSON 거절은 기존 검사에서 통과했지만 **문법은 맞고 상태가 잘못된 저장**은 별개다.

추가 코드 감사에서 `enemies`, `buff`, 카운터, 수치 범위의 상세 타입·구조 검증도 부족함을 확인했다. 그 모든 변형의 크래시를 실행했다고 주장하지 않는다. 이번 확정 반례는 위5발 계획 수용뿐이다.
