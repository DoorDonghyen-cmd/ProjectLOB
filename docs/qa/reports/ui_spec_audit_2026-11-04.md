# UI 규격화 현황 점검 — 2026-11-04

**판정: 공통 외형과 일부 기반 규칙은 있지만, 역할별 UI 규격과 적용 체계는 미완성이다.** 색·프레임이 비슷하다는 사실만으로 규격화 완료라고 볼 수 없다. 반대로 크기가 여러 개라는 사실만으로 설계 오류라고 단정할 수도 없다. 화면/역할에 따른 차이의 근거와 적용 경로가 명확한지가 기준이다.

사용자가 작업 전에 규격화 여부 확인을 요청했다. 제품 수정 없이 활성 진입의 공통 셸, 캐릭터 선택, 상점, 현행 정비소·결과, 관문, 지도, 상세창, 실제 전투 HUD와 공통 리소스를 대조했다. 정적 표본28개 파일이며 프로젝트 전체의 모든 상태를 전수 검사했다고 주장하지 않는다. [선언·소스 해시 목록](ui_spec_audit_2026-11-04/inventory.json). 정적 씬의 숨긴 노드와 런타임 덮어쓰기 전 값도 포함되므로 선언 수를 위반 건수로 세지 않았다. 현재 표시는 직전 [실화면 비평](ui_visual_critique_2026-11-04.md)과 [105상태 실측](ui_geometry_2026-11-04.md)을 함께 사용했다.

## 대표 근거

### 버튼 크기와 확장 정책

논리 단위 기준으로 다음 선언/공통 코드가 공존한다. 이는 현재 값 목록이며 새 규격표가 아니다.

| 위치/역할 | 현재 높이·폭 정책 |
|---|---|
| 전투 메뉴·냉각·교체 | 최소 높이44 |
| 전투 사격 | 최소 높이50 |
| 공통 `_button()` | 최소 높이52, 남는 폭 확장 |
| 선택 화면 돌아가기·규칙 상세 | 최소 높이48 |
| 선택 화면 등반 시작 | 최소250×54 |
| 상점 구매 | 최소 높이56, 상세 열 폭 채움 |
| 상점 나가기 | 최소 높이58, 열 폭 채움 |
| 정비소 `_place_action()` | 기본216×52, 오른쪽 내용 폭 정렬 |
| 캠페인 상태줄의 작은 버튼 | 최소78×40 |
| 공통 상세창 닫기/확정 | 닫기90×48, 확정/취소 높이52 |

전투44/50과 메뉴52 같은 차이는 기존 의도된 화면 규격일 수 있다. 문제는 이를 ‘전투 보조 / 일반 행동 / 아이콘 / 탐색’ 같은 역할 규칙과 폭 정책으로 연결하지 않고 각 파일에서 지정한다는 점이다. 정비소는 이미 확장하지 않으므로 공통 버튼을 일괄 수정하는 방법도 부적절하다.

### 패딩의 원본이 여러 곳에 있음

- `ui-line-theme.md`와 정답 HTML `theme_line.css:49`는 일반 버튼 좌우12를 제시한다.
- `screen.gd:_console_style()`은 좌우16·상하12로 바꾼다. `_panel()`은 이 공통 함수를 사용한다.
- `equipment_screen.gd`의 선택 버튼은 좌우14를 별도 지정한다.
- `console_button_normal.tres`와 `shop_preview_key_normal.tres` 자체 content margin은0이며, 씬/내용 노드가 다시 여백을 정한다.
- 복제된 StyleBox를 사용하는 방법 자체는 정상이며 테두리 여백과 내용 여백도 다른 개념이다. 하지만 현재 문서→공통 리소스→호출부→실제 노드 중 최종 규격의 책임 위치가 역할별로 정리되어 있지 않다.

### 글자 역할과 선명도 규칙의 충돌

`ui_readability.gd`는 비전투 글자를16단위로 정리하지만 `LineSkin.font_step()`은12/16/24/32로 정리한다. 후자는 전투 readout과 장소 title/hint에서 호출된다. 비전투 장소에는 공통16단위 처리가 다시 적용되며, 라이브 HUD는 별도 경로로 관리된다. **전투와 비전투의 차이는 문서상 의도된 예외**이지만, 장소처럼 여러 경로가 겹치는 사용처에서는 처음 요청한 크기와 최종 크기가 달라진다. 제목/본문 역할을 먼저 고정하고 최종 렌더 기준으로 확인할 필요가 있다.

선택한28개 파일에는 `Title/Body/Caption/PrimaryAction` 등 역할별 Theme variation 사용이 없었다. 다만 다른 경로의 `LineRouteRow` 같은 제한적인 variation 사례는 존재한다. 프로젝트 전체에 variation이 전혀 없다고 주장하지 않는다. Godot variation만이 유일한 구현 방법도 아니며, 명확한 역할별 공통 함수/컴포넌트로 관리할 수도 있다.

### 숫자가 많은 것과 규격이 없는 것은 구분

정적 표본의 간격 리터럴은0,2,3,4,5,6,7,8,10,12,14,16,18,20,22,24였다. 작은 게이지/도트 안쪽 간격과 큰 화면 영역 간격은 다를 수 있다. 이를16개 위반으로 세지 않았다. 다만 이 값들이 ‘요소 내부 / 카드 사이 / 영역 사이 / 화면 가장자리’ 같은 공통 단계로 연결되지 않고 개별 호출에 남아 있다는 것이 관리상의 공백이다.

## 작업 전 필요한 정리

다음은 후속 규격화의 범위 제안이며 새로운 수치/레이아웃을 확정한 것은 아니다.

1. **역할 정의:** 제목·본문·보조·핵심 수치, 주 행동·보조 행동·아이콘 버튼, 선택 카드·정보 패널·모달을 구분한다. 같은 색/크기를 모든 역할에 강제하는 방식으로 규격화하지 않는다.
2. **크기와 공간 규칙:** 버튼별 높이·내용 기준 폭·폭 상한·확장 허용 조건·터치 영역, 여백/간격 단계, 카드의 내용/그림 비율과 최소 높이를 정한다. 정상 스크롤은 허용한다.
3. **적용 경로:** 현재 방향 문서의 기준과 공통 Theme/StyleBox/컴포넌트를 대응시키고 화면별 override는 이유를 남긴다. 전투 HUD와 기존 선택 화면처럼 의도된 예외를 명시한다.
4. **대표 상태 확인:** 현재 배치에서 기본/선택/비활성/긴 문구/큰 글씨/작은 화면의 역할별 최종 크기를 확인한다. 기존 기능·저장 검사와 별도로 규격의 실제 적용을 검사한다.
5. **순차 정리:** 공통 규격을 정리한 다음 정비소→결과→상점에 적용 여부를 확인한다. 이번 진단을 전체 화면 재배치·공통 버튼 일괄 변경 승인으로 해석하지 않는다.

## 이번 작업의 경계

- 게임 코드·씬·배치·수치·텍스트·아트 수정 없음. 규격화 점검과 문서 기록만 수행했다.
- 기존 제품/검사743개 파일이 모바일 대응 전 스냅샷과 바이트 단위 일치함을 재확인했다. 이번 정적 조사 때문에 새 실행 테스트나 미감 합격 점수를 만들지 않았다.
- 기존 실캡처/실측의 소스 해시와 현재 파일을 대조했다. Android 실기기 안전 영역·사람 체감과 모든 UI 상태의 전수 검증은 포함하지 않는다.
