# HTML UI 목업 전체 조작 검토

검토일: 2026-11-01. 사용자 요청: “전체 조작까지 검토해 줘”.

후속 상태: 사용자 승인으로 F01–F07, F09를 수정하고 재검증했다. [조작 안정화 1·2단계 결과](ui_prototype_stabilization_2026-11-01.md). 아래는 수정 전 해시와 재현 기록이며 이력으로 보존한다. 작은 화면 크기(F08)와 현행 탄창 UX/Godot 연결은 후속이다.

## 판단

지도에서 선택하고 전투를 치른 뒤 보상·정비로 이어지는 기본 흐름은 동작한다. 선택지 옆에 결과와 비용을 보여 주고, 같은 위치에서 확정하도록 만든 구조는 유지할 가치가 있다. 그러나 **승패 확정, 화면 전환, 창이 열린 상태의 입력 처리**에 재현 가능한 결함이 있다. 이 부분과 비용 표시를 먼저 정리해야 실제 플레이로 UX를 판단하기 좋다.

이번 결과는 **HTML 목업의 조작 검토**다. Godot 실행본의 결함으로 일반화하지 않는다. 목업은 손패에서 장전하고 마지막에 넣은 탄부터 쏘는 이전 흐름이며, 현재 Godot의 탄창 자동 장전·부분 사격·선택 후 즉시 빼내기와 다르다. 공통 화면 구성은 참고할 수 있지만 전투 입력 흐름을 그대로 이식하는 것은 권하지 않는다.

## 검토 대상과 방법

- 대상: [index.html](ui_prototype_2026-10-31/index.html)
- 실행: `http://127.0.0.1:8765/index.html`. 해당 목업 폴더만 제공하는 로컬 서버.
- 사용자 탭과 분리한 검토 탭에서 공개 버튼·우클릭·키보드·더블클릭으로 진행했다. 게임 내부 변수를 주입하거나 숨은 함수를 호출하지 않았다.
- 화면: 1280×800, 1008×630, 1008×454. 목업의 20:9 / 16:10 전환도 확인했다. 검토 후 브라우저 임시 화면 크기는 복원했다.
- 작업 트리에 기존 변경이 많아 커밋만으로 버전을 특정하지 않았다. HEAD 참고값: `197c694`.
- HTML SHA-256: `ad11c4b2771ddfb79367a4328efa329b7c0eef690b3940a783b79616377c52e3`. 검토 전후 동일.
- `assets/game_data.js` SHA-256: `93cced12952fd5cbb696785b9cb8d7b39bd2494c42ffd0ff4c50ec1f2d9fe198`.
- 모든 조작의 DOM 기록, 주요 화면, 오류 로그: [증거 목록](../../../qa_runtime/ui_prototype_interaction_review_20261101/evidence_manifest.json). 아래 증거 번호는 이 폴더의 파일명 접두사다.

## 우선 수정할 사항

### F01 · P1 · 승리 뒤 재사격으로 크레딧 중복 지급

**실제 일반 전투를 완료한 뒤 재현했다.** 승리 화면 바로 가기로 만든 상태가 아니다.

1. 지도에서 이어진 두 번째 전투에서 적을 모두 처치한다. 크레딧이 81 → 87로 증가한다.
2. 보상을 받기 전에 남아 있는 냉각탄을 클릭한다. 승리 안내가 사라지고 장전이 가능하다.
3. 적이 없는 상태에서 사격한다. 크레딧이 87 → 93으로 다시 증가한다.

승리 확정 상태와 보상 지급 완료 상태를 따로 보관하고, 종료된 전투에는 장전·사격·재장전 명령을 받지 않아야 한다. 보상 지급은 같은 전투에서 한 번만 처리해야 한다.

- 관련 코드: `fire()` 572–575행, `win()` 647–652행. 사격은 처리 중/장전 여부만 검사하고, 승리는 호출될 때마다 크레딧을 더한다.
- 증거: [첫 승리](../../../qa_runtime/ui_prototype_interaction_review_20261101/22_win_before_repeat.jpg), [재지급](../../../qa_runtime/ui_prototype_interaction_review_20261101/24_duplicate_victory_credit.jpg), `23_win_still_accepts_cards.txt`.

### F02 · P1 · 보상 더블클릭이 다음 장소 이동까지 실행

1. 보상 화면에서 `1장 확보`를 더블클릭한다.
2. 첫 클릭으로 탄환을 한 장 받고 지도에 돌아간다.
3. 두 번째 클릭이 같은 위치에 생긴 지도의 `이동` 버튼에 전달되어 다음 전투에 바로 들어간다.

두 번 재현했다. 덱은 10 → 11장으로 한 번만 늘었지만, 경로를 검토하거나 선택할 틈 없이 다음 전투가 시작됐다. 상점 구매 더블클릭은 한 번만 결제되어 이 경우와 다르다.

화면 전환을 시작한 입력 묶음이 다음 화면의 명령까지 실행하지 않도록 해야 한다. 장소 확정과 다음 이동을 별개의 사용자 입력으로 처리한다.

- 관련 코드: `confirmPlace()` 706행 이후 → `finishNode()` 293행 이후 → `go` 클릭 처리 931행. 화면 교체 후 연속 입력을 제한하는 처리가 없다.
- 증거: `69_reward_double_click.txt`, [확보 전](../../../qa_runtime/ui_prototype_interaction_review_20261101/71_reward_before_double.jpg), [바로 다음 전투](../../../qa_runtime/ui_prototype_interaction_review_20261101/72_reward_double_enters_combat.jpg).

### F03 · P1 · 메뉴 뒤의 이동 버튼을 키보드로 실행 가능

1. 지도에서 게임 메뉴를 연다.
2. `도움말`에 초점을 둔 뒤 Shift+Tab을 누른다.
3. 메뉴가 열려 있는데도 초점이 뒤쪽 지도의 `이동`으로 넘어간다.
4. Enter를 누르면 전투로 이동한다.

창을 열 때 내부로 초점을 옮기고, Tab 이동을 내부에 유지하며, 배경 명령도 상태 검사로 차단해야 한다. 닫을 때는 원래 버튼으로 초점을 돌려준다. 구매나 사격의 배경 실행까지 재현한 것은 아니며, **이동 실행을 직접 확인했다.**

- 관련 코드: `renderOverlay()` 779행 이후, `go` 처리 931행.
- 증거: [초점 이탈](../../../qa_runtime/ui_prototype_interaction_review_20261101/18_modal_focus_escape.jpg), [배경 이동 실행](../../../qa_runtime/ui_prototype_interaction_review_20261101/19_modal_background_move.jpg).

### F04 · P1 · 비상 보급의 두 번째 사용 비용이 안내와 다름

관문전에서 탄약을 모두 소진하고 비상 보급을 두 번 사용했다. 버튼은 두 번째에도 `기본탄 4발 · 적 2행동`으로 표시된다. 실제 실행 비용은 사용 횟수에 따라 늘어나 두 번째에는 **적 3행동**이다.

도달 즉시 패배하는 게임에서 추가 적 행동은 선택 결과를 바꾸는 핵심 비용이다. 버튼·미리보기·실행이 같은 비용 계산을 사용해야 한다.

- 표시: 488행의 고정 `적 2행동`.
- 실행: 636행의 `C.emergency++; actions = 1 + C.emergency`.
- 증거: `54_ammunition_exhausted.txt`, `55_first_emergency.txt`, [두 번째 버튼](../../../qa_runtime/ui_prototype_interaction_review_20261101/56_second_emergency_label.jpg), `57_second_emergency_result.txt`.
- 비용 판정은 실제 두 번의 조작과 실행 코드 대조에 근거한다. 애니메이션 중간 화면의 지휘 턴 숫자만으로 행동 횟수를 추정하지 않았다.

### F05 · P2 · 사격 중 게임 메뉴에서 재시작하면 이전 처리가 남음

관문전에서 네 발 사격 직후 게임 메뉴 → `처음부터`를 실행했다. 화면은 새 지도에 돌아왔지만 이전 사격이 계속되어 다음 오류를 남겼다.

`TypeError: Cannot read properties of null (reading 'clientWidth')`

호출 위치는 `fieldGeom:460 → enemyCenter:569 → fireSteps:587`이다. 이후 다른 화면으로 이동할 수 있었으므로 영구 정지로 판정하지는 않았다. 상단 목업 탭으로 사격 중 상점에 이동한 경우에는 새 오류가 발생하지 않았다.

- 원인: 상단 탭 전환과 도구 모음 재시작은 `epoch`를 갱신하지만, 게임 메뉴의 재시작 처리(946행)는 `newRun()`만 호출한다.
- 권장: 모든 새 게임·재시도·장면 이탈 경로가 같은 실행 취소 절차를 사용하도록 통합한다.
- 증거: `47_restart_during_fire.txt`, [오류 로그](../../../qa_runtime/ui_prototype_interaction_review_20261101/48_restart_error_log.json).
- 추가 관찰: 사격 중 연 메뉴는 사격 완료의 화면 갱신으로 닫혔다. 메뉴를 열었을 때 사격을 계속할지와 창을 유지할지도 일관되게 정해야 한다.

### F06 · P2 · 공방에서 개조 대상이 없어도 방문을 소비

공방 바로 가기를 이용해 피해 3 기본탄 세 장을 모두 개조한 뒤 다시 방문했다. 빌드에는 피해 4 기본탄 네 장만 있었지만, 공방은 계속 `피해 3 → 피해 4`를 제안하고 `작업하기`를 허용했다. 실행 후 덱은 그대로이고 방문 진행만 증가했다.

실제 대상이 있을 때만 개조를 활성화하고, 대상이 없으면 그 이유를 표시해야 한다. 기본탄 등급이 섞여 있을 때에는 어떤 탄이 개조·제거·교체되는지도 보여 주는 것이 좋다.

- 관련 코드: 공방 선택지 658행 이후, `confirmPlace()` 710행. 대상 검색 실패 후에도 방문이 완료된다.
- 증거: `39_no_eligible_basic_before.txt`, [대상 없는 제안](../../../qa_runtime/ui_prototype_interaction_review_20261101/40_tune_without_target.jpg), `41_no_change_after_tune.txt`.
- 반복 방문은 공개된 목업 바로 가기로 만든 경계 조건이다. 정상 경로에서 이만큼 연속 방문했다고 주장하지 않는다.

### F07 · P2 · 과열 시 실제 발사 수와 소진되는 탄의 차이가 드러나지 않음

관문전에서 발열 10/15, 남은 탄 8장 상태로 `기본탄(열 3) → 기본탄(열 2) → 기본탄(열 2) → 냉각탄`을 장전했다. 두 번째 탄에서 과열되어 실제 피해는 두 발만 적용되었다. 그런데 버튼은 `4발 사격`이고, 남은 탄은 8 → 4장으로 줄어 뒤의 두 장도 소실됐다.

도움말은 “그 탄까지 쏘고 강제 재장전”이라고만 안내한다. **미발사 탄 폐기가 의도인지 먼저 정해야 한다.** 보존할 규칙이라면 실제 발사한 탄만 소비하고, 폐기가 의도라면 미발사/폐기되는 탄을 사격 전에 구분해야 한다. 현재는 사용자가 전체 비용을 읽기 어렵다.

- 관련 코드: 607행에서 실제 `sim.shots`가 아니라 전체 `C.plan`을 소진한다.
- 증거: [사격 전](../../../qa_runtime/ui_prototype_interaction_review_20261101/50_overheat_plan.jpg), [사격 후](../../../qa_runtime/ui_prototype_interaction_review_20261101/51_overheat_four_consumed.jpg), `52_help.txt`.
- 분류: 재현한 동작과 안내의 차이. 사용자에게 확정받지 않은 폐기 규칙을 임의로 버그/정답으로 결정하지 않는다.

### F08 · P2 · 작은 화면에서는 주요 입력과 글자가 지나치게 축소

화면 전체를 같은 비율로 줄여 배치는 유지되지만, 입력 면적과 글자까지 함께 작아진다.

| 브라우저 화면 | 재장전 버튼 높이 | 사격 버튼 높이 | 메뉴 버튼 높이 |
| --- | ---: | ---: | ---: |
| 1008×630, 20:9 목업 | 28.3px | 32.9px | 19.3px |
| 1008×454, 20:9 목업 | 23.6px | 27.4px | 16.1px |

1008×454에서는 카드 기본 글자 16px도 전체 축소 후 약 7.6px에 해당한다. 카드 자체는 누를 면적이 있지만 상단 메뉴·순서 칩·하단 행동은 별도 조정이 필요하다. 전장 표시 크기와 UI의 최소 입력/글자 크기를 분리하고, 모바일에서 보조 문구를 줄이는 방향을 권한다.

- 관련 코드: `fit()` 885행 이후의 전체 `transform: scale(...)`.
- 증거: [1008×630](../../../qa_runtime/ui_prototype_interaction_review_20261101/65_combat_1008x630.jpg), [1008×454](../../../qa_runtime/ui_prototype_interaction_review_20261101/66_combat_1008x454.jpg), [실측값](../../../qa_runtime/ui_prototype_interaction_review_20261101/66_mobile_metrics.json).
- 목업 도구 모음이 화면 높이 일부를 차지한 조건이다. Android 실기기에서 같은 픽셀 크기나 터치 실패율을 측정한 것은 아니다.

### F09 · P3 · 구매 완료 후에도 미래 구매 예측이 남음

34 Cr에서 30 Cr 파츠를 구매해 잔액이 4 Cr가 되었고 상품은 구매 완료로 처리됐다. 구매 버튼과 새 진열은 정상적으로 비활성화되었다. 그러나 결과 패널은 `파츠 4 → 5/5`, `4 → -26 Cr`, `구매 후 -26 Cr`를 계속 표시했다.

실제 마이너스 결제가 일어난 것은 아니다. 구매 완료 후에는 완료 결과를 보여 주고, 다른 상품을 고를 때 새 구매 예측을 보여 주는 편이 명확하다.

- 관련 코드: `renderShop()` 723행 이후.
- 증거: [구매 후 화면](../../../qa_runtime/ui_prototype_interaction_review_20261101/34_shop_low_funds.jpg).

## 실행 환경과 목업의 한계

- `목업 보고서` 링크는 현재 서버에서 404였다. 링크가 목업 폴더의 상위 파일을 가리키지만 로컬 서버는 목업 폴더만 제공하기 때문이다. 이는 게임 상태 결함과 구분할 **현재 실행 경로의 제공 범위 문제**다. 원본 [목업 보고서](ui_frame_mockups_2026-10-31.md)는 로컬에 있다. 증거: `70_report_link_404.jpg`.
- 바로 가기 화면에서 공방/탄약고 작업을 반복하면 같은 진행 상태에 결과를 누적할 수 있고 진행 표기가 8/8을 넘었다. 이는 경계 조건을 만들기 위해 사용한 목업 도구의 특성이다. 정상 1구역 경로의 진행 증거로 사용하지 않는다.
- 보고서 링크를 연 뒤 돌아왔을 때 진행이 새로 초기화된 것을 관찰했다. 목업은 저장·복원 검증용이 아니다.
- 전투 계산은 목업에 안내된 대로 일부 파츠·코어·세부 규칙을 생략한다. 구매된 파츠의 실제 전투 효과나 본편 밸런스를 통과 판정하지 않는다.
- Android 실기기 터치·길게 누르기·스크롤 충돌·진동·발열·지속 성능, 전체 캠페인 완주, 최대 가방/파츠 슬롯의 모든 조합, 사용자 이해도와 재미는 미검증이다. 우클릭 상세 성공을 길게 누르기 성공으로 대체하지 않았다.
- `28_shop_entry`는 실제 상점 진입이 아니라 지도상의 접근 불가 상점 선택 기록이다. 실제 상점 조작은 29번부터다. `62_elite_reinforcement`는 후속 적 대기 표시와 사격 기록이며 실제 증원 등장 증거는 아니다.

## 다음 적용 순서 제안

1. 승패 확정·중복 보상 차단, 화면 전환 뒤 연속 입력 차단, 메뉴 배경 입력 차단, 재시작 시 진행 중 처리 취소를 함께 정리한다.
2. 비상 보급 비용을 실행과 일치시키고, 과열 시 미발사 탄 처리를 확정해 미리보기에 반영한다.
3. 공방 대상 유효성·구매 완료 상태를 실제 보유 상태에 맞춘다.
4. 현재 Godot의 탄창/빼내기 조작에 맞춰 전투 화면을 연결하고, 모바일 입력 면적과 글자 크기를 확보한다.
5. 그 상태에서 동일 흐름을 다시 플레이하고 사용자의 선택 이해도·미감을 확인한다. 정상 클릭 성공만으로 재미나 최종 UI 완성도를 판정하지 않는다.
