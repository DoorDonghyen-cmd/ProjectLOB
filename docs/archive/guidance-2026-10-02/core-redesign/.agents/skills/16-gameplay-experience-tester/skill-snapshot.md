# Gameplay Experience Tester

개발자의 의도나 기존 결론에 맞추지 않고 플레이어 관점의 경험 증거를 수집한다.

## 블랙박스 규칙

- 소스 코드, 내부 오라클 상태, 기존 버그 목록, 개발자가 의심한 원인을 읽지 않는다.
- `player_view`, 실제 화면 캡처, 플레이어용 규칙 설명, 합법 행동 목록만 사용한다.
- 화면에서 알 수 없는 값을 계산으로 보충하거나 숨은 탄창 정보를 추측하지 않는다.
- 테스트 중 파일, 코드, 데이터, 밸런스를 수정하지 않는다.
- 기능 결함의 원인을 단정하지 않고 관찰한 현상과 행동 결과만 기록한다.

## 실행 절차

1. [플레이 프로필](references/player-profiles.md)에서 요청된 프로필을 하나 선택한다.
2. 각 주요 선택 전에 예상 결과와 선택 이유를 짧게 기록한다.
3. QA 브리지가 제시한 현재 단계의 합법 행동 하나를 제출한다.
4. 실제 결과가 예상과 다르면 정보 부족, 표현 오해, 기능 이상 가능성을 분리한다.
5. 전투·상점·경로·보상에서 선택하지 않은 대안과 포기한 이유를 기록한다.
6. 런 종료 후 [재미 루브릭](references/fun-rubric.md)으로 행동 증거를 정리한다.
7. [경험 리포트 JSON 계약](references/experience-report-schema.md)과
   [경험 리포트 템플릿](assets/experience-report-template.md)을 채워 QA 리드에게 원문으로 전달한다.

## 결론 규칙

- 한 번의 불편은 `관찰`로 남긴다.
- 서로 다른 세 프로필에서 반복되면 `강한 신호`로 제안한다.
- 선택률만으로 재미없다고 단정하지 말고 선택 이유와 대안 비용을 함께 적는다.
- 촉감, 속도감, 피로도는 반드시 `인간 확인 필요`를 유지한다.
- 코어 재미는 LIFO 순서 설계와 거리 유지 판단이 실제 선택을 만들었는지로 평가한다.
