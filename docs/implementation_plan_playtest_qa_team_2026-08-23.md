# 전용 플레이 QA 팀 구현 계획

> 작성일: 2026-08-23
> 세션 ID: `codex0823-qa-team`
> 상태: Phase A~F 완료
> 기획 정본: `docs/design_playtest_qa_team_2026-08-23.md`

## 1. 결론

ProjectLoB에는 `15-gameplay-qa-lead`, `16-gameplay-experience-tester` 두 프로젝트 전용
스킬을 추가하고 기존 `12-combat-simulator`를 세 번째 독립 검증자로 사용한다.

구현은 역할 문서부터 시작하되, 실제 플레이를 가능하게 하는 Godot 상태/행동 브리지와
재현 가능한 RNG 분리를 단계적으로 연결한다. 첫 버전부터 전체 35층 자동 플레이를 만들지
않고 고정 전투 → 실제 UI 흐름 → 1~2구역 → 전체 런 순서로 확장한다.

## 2. 범위

### 포함

- 프로젝트 전용 QA 스킬 2종과 UI metadata
- 공용 테스트 차터, 독립 보고서, 통합 보고서 템플릿
- 테스트 전용 세이브·로그 격리 실행기
- Godot 상태/행동 JSON 브리지
- 플레이어 공개 상태와 내부 오라클 상태 분리
- 기능 QA용 의미 단위 UI 액션과 체크포인트 캡처
- 초심자/공격형/보수형/실험형 정책 규격
- 게임플레이 RNG와 FX RNG 분리 및 seed 기록
- 재미 지표 집계와 기존 `PlaytestLogger` 확장
- 전체 회귀 및 QA 브리지 전용 테스트

### 제외

- 테스터가 코드나 밸런스를 자동 수정하는 기능
- 운영 빌드의 원격 로그 업로드
- 인간 플레이테스트를 자동 결과로 완전히 대체하는 판정
- 픽셀 좌표 기반 OS 마우스/키보드 매크로
- 첫 구현에서 모바일 실기 자동화

## 4. 구현 단계

### Phase A — 직원 역할과 계약

1. 공식 `skill-creator` 초기화 스크립트로 프로젝트의 `.agents/skills` 아래에 두 스킬을 생성한다.
2. `SKILL.md`에는 트리거, 읽기 범위, 금지 행동, 실행 순서, 산출물만 간결하게 둔다.
3. 상세 루브릭과 프로필은 `references/`, 보고서 양식은 `assets/`로 분리한다.
4. 두 스킬의 `agents/openai.yaml`을 생성하고 `quick_validate.py`로 검증한다.
5. 기존 `12-combat-simulator`, `05-bug-report`, `09-creative-director` 연결 규칙을 명시한다.

완료 조건:

- 두 스킬이 올바른 요청에서만 발동한다.
- 기능 QA가 재미를 확정하거나 경험 QA가 버그 원인을 추측하지 않는다.
- 테스트 중 소스 수정 금지 규칙이 양쪽에 존재한다.

### Phase B — 고정 전투 QA 브리지 MVP

1. `qa_session_runner.gd`가 전용 APPDATA와 manifest를 준비하고 `qa_runtime/`을 Git에서 제외한다.
2. `qa_bridge.gd`가 고정 개발자 전투를 시작하고 `player_view`와 `oracle_state`를 기록한다.
3. 합법 행동 목록과 단계 번호를 포함한 상태 계약을 추가한다.
4. `load`, `confirm_load`, `fire`, `reload`, `eject`를 실제 `CombatManager`에 전달한다.
5. 행동 결과를 기존 `PlaytestLogger` 형식과 함께 기록한다.

완료 조건:

- 최소 20단계 상태/행동 왕복이 가능하다.
- 잘못된 단계·탄환·대상 행동은 상태를 바꾸지 않고 거절된다.
- `player_view`에는 은폐된 탄창과 내부 HP 등 비공개 정보가 없다.
- 동일 행동열은 동일 전투 결과를 만든다.

### Phase C — 실제 씬과 UI 체크포인트

> **완료(2026-08-23):** 실제 `combat_scene.tscn` 콜백 기반 의미 행동, 공개 컨트롤
> 상태 JSON, 상점 데이터↔렌더 설명 정합 검사, Viewport PNG 캡처와 headless 인프라
> 폴백, 9개 화면 체크포인트 실행기를 구현했다.

1. `combat_scene.tscn`을 실제로 인스턴스화한다.
2. 메인, 구역 선택, 준비실, 맵, 장전, 보상, 상점의 의미 단위 UI 액션을 연결한다.
3. 컨트롤 이름, visible, disabled, text, rect 정보를 상태에 포함한다.
4. 체크포인트 PNG 캡처를 추가하고 실패 시 인프라 오류로 분류한다.
5. 기존 `suite_ui_smoke.gd`와 중복되는 단순 존재 검사는 재사용한다.

완료 조건:

- 메인 → 전투 → 보상 → 상점 흐름을 실제 씬으로 재생한다.
- 리롤 후 가운데 카드처럼 선택 상태가 남는 결함을 상태와 이미지 양쪽에서 검출할 수 있다.
- 화면 캡처가 없는 환경에서도 의미 단위 UI 계약 검증은 계속 실행된다.

### Phase D — 재현 가능한 전체 런

> **완료(2026-08-23):** `map`, `encounter`, `reward`, `shop`, `event`, `combat` 게임플레이
> 스트림과 FX 스트림을 분리하고, manifest v2·`PlaytestLogger` v3에 seed와 세션 ID를
> 기록했다. 실제 메인 씬을 깨끗한 전용 세이브로 2구역 재생해 46개 의미 행동과 13개
> 노드를 통과했으며, 동일 seed 독립 실행에서 행동열·진행 상태·게임플레이 RNG 상태가
> 일치하고 FX seed만 달라지는 것을 확인했다. 행동마다 `progress.json`을 갱신한다.

1. 맵·적 편성·보상·상점의 게임플레이 RNG를 명시적 스트림으로 분리한다.
2. 흔들림·트윈 지연 같은 FX RNG가 게임플레이 결과에 영향을 주지 않게 한다.
3. `PlaytestLogger`를 스키마 v3으로 올리고 manifest의 게임플레이 seed와 세션 ID를 기록한다.
4. `choose_route`, `choose_reward`, `buy`, `reroll`, `use_maintenance`, `continue_section` 행동을 연결한다.
5. 깨끗한 세이브와 지정 로드아웃으로 1~2구역을 재생한다.

완료 조건:

- 동일 커밋·세이브·seed·행동열의 JSON 핵심 결과가 동일하다.
- 실제 사용자 세이브와 플레이테스트 로그 폴더를 오염시키지 않는다.
- 강제 종료 후에도 마지막 완료 전투와 행동 단계가 보존된다.

### Phase E — 재미 프로필과 지표

> **완료(2026-08-23):** 프로필 정책은 경험 테스터 reference에만 두고, 코드는
> `player_view`·선택 이유·포기한 대안·실제 결과를 받는 보고서 계약만 구현했다.
> 선택 집중도, 리로드/무효 행동, 최소 거리, 과잉 피해, 미사용 전술탄,
> 파츠·경로 중복률을 개별 증거로 집계하며 종합 점수는 만들지 않는다. 동일 시작
> 조건의 네 보고서 비교, 동일 행동열 거절, 대안별 지배 격차, `strong_signal`·
> `hypothesis`·`human_confirmation` 통합을 회귀로 고정했다.

1. 네 프로필의 선택 원칙을 코드가 아닌 에이전트 reference로 정의한다.
2. 브리지는 선택지를 강제하지 않고 합법 행동과 플레이어 공개 정보만 제공한다.
3. 선택 집중도, 리로드/무효 행동 비중, 최소 거리, 과잉 피해, 전술탄 미사용,
   파츠·경로 중복률을 집계한다.
4. 단일 점수 대신 증거가 포함된 항목별 판정을 생성한다.
5. 동일 시작 조건의 네 보고서를 비교하는 통합기를 추가한다.

완료 조건:

- 프로필 이름만 다른 동일 행동열을 성공으로 인정하지 않는다.
- 지배 전략 신호에는 어떤 선택이 어떤 대안을 얼마나 밀어냈는지 근거가 있다.
- 재미 결론은 `강한 신호`, `가설`, `인간 확인` 중 하나로 표시된다.

### Phase F — 팀 실행과 전방 검증

> **완료(2026-08-23):** 기능 QA·초심자 경험 QA·전투 시뮬레이터를 서로의 결론 없이 실행하고,
> 세 원본이 끝난 뒤에만 QA 리드에게 공유했다. 정상 sample A는 오탐 없이 PASS, seeded sample B는
> 사전 답안 없이 기능 FAIL 후보와 구매 포기 경험 신호로 검출했다. 현 빌드의 실제 상점 리롤은 정상이며
> seeded fixture를 제품 버그로 등록하지 않았다. 최근 인간 로그 16발은 명중·관통 공식 불일치 0건이었고,
> 전체 회귀는 **3,562 통과 / 0 실패 / 기존 경보 3**이다.

1. 한 요청에서 세 역할을 독립 컨텍스트로 동시에 실행한다.
2. 각 역할에는 원본 artifact와 필요한 최소 문맥만 전달한다.
3. 독립 보고 완료 후 QA 리드에게 원문 결과를 전달해 통합시킨다.
4. 의도적으로 준비한 샘플 결함과 정상 시나리오로 오탐·미탐을 확인한다.
5. 실제 최근 플레이테스트 JSON 하나를 재분석해 기존 인간 결론과 비교한다.

완료 조건:

- 경험 테스터가 미리 알려주지 않은 문제를 독립적으로 발견할 수 있다.
- 정상 동작을 버그로 오인한 항목은 근거 부족으로 통합 리포트에서 분리된다.
- 확정 버그는 기존 버그 템플릿과 상태 체계를 그대로 사용한다.

## 5. 테스트 전략

### 자동 회귀

- manifest 필수 필드와 schema 버전
- 단계 번호의 단조 증가와 중복 행동 거절
- 화면별 합법 행동 계약
- 공개 상태의 숨김 정보 누출 방지
- 전용 APPDATA 격리
- 같은 seed와 행동열의 결과 재현
- QA 리포트의 필수 섹션과 심각도 값
- 기존 전체 `run_all.gd` 회귀

### 수동 확인

- 이미지가 실제 화면과 일치하는지
- 초심자 프로필이 개발자 지식 없이 행동하는지
- 재미 가설과 기능 버그가 섞이지 않는지
- 전체 QA 요청 한 문장으로 세 역할과 통합 보고가 이어지는지

## 6. 운영 명령 계약

사용자는 구현 후 다음처럼 요청한다.

- `QA 팀으로 이번 변경분 빠른 검증해 줘`
- `상점과 조합탄 변경을 QA 팀으로 집중 검증해 줘`
- `재미 QA로 1~2구역 네 프로필을 돌려 줘`
- `릴리스 후보 빌드를 QA 팀 전체 검증해 줘`

주 에이전트는 요청을 테스트 모드로 변환하고 커밋되지 않은 변경이 있으면 manifest에
`dirty_worktree: true`와 대상 diff를 기록한다. 사용자 소유 변경은 수정하거나 스테이징하지 않는다.

## 7. 예상 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 역할만 나뉘고 결론이 서로 오염됨 | 독립 컨텍스트, 결과 후공유, 입력 정보 표 적용 |
| 브리지가 실제 UI를 우회함 | 의미 단위 버튼 신호와 실제 씬 흐름 사용, 내부 API 전용 결과와 구분 |
| 전역 RNG가 재현을 깨뜨림 | 게임플레이와 FX RNG 분리 후 전체 런 개방 |
| QA가 사용자 세이브를 덮음 | 세션별 전용 APPDATA와 경로 검증 |
| 재미를 자동 점수로 과신함 | 단일 종합 점수 금지, 인간 확인 상태 유지 |
| 보고서가 과다 생성됨 | 런타임 원본 비커밋, 통합 리포트만 보존 |
| 테스터가 수정까지 수행함 | 읽기·실행·보고 전용 규칙, 수정은 별도 개발 요청으로 분리 |

## 8. 권장 착수 단위

첫 구현 묶음은 Phase A와 Phase B까지만 진행한다.

- 두 직원이 실제로 서로 다른 보고서를 만드는지 먼저 확인할 수 있다.
- 고정 전투만 사용하므로 RNG 분리와 전체 UI 자동화 없이도 직접 행동 루프를 검증할 수 있다.
- 이 단계의 결과가 유효할 때만 Phase C~F의 제작비를 지불한다.

Phase A~B 승인 기준은 `탄환 전문축 QA` 고정 전투 한 건을 두 역할이 독립 수행하고,
시뮬레이터 대조가 포함된 통합 보고서를 생성하는 것이다.
