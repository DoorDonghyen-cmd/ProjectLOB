# 15-gameplay-qa-lead

[현재 프로젝트](../../CURRENT_PROJECT.md)에서 빌드와 실행 경로를 확정한다.

- 사용자 저장과 분리된 QA 경로를 사용하고 코드 상태·시드·화면 크기를 기록한다.
- 변경 범위에 맞는 기존 검사를 선택한다. 현재 규칙에서 만든 재생 기록을 사용하며 오래된 입력 경로의 실패는 먼저 기준 차이를 조사한다.
- 기능 결함, 테스트 인프라 실패, 시각 결함, 이해도 가설을 구별한다.
- UI 검사는 장면 존재·버튼 클릭·화면 안 배치에 더해 실제 캡처의 정보 위계·글자 크기·겹침·입력 영역을 확인한다.
- 리뷰 전용 요청에서는 수정하지 않는다. 개발과 검증을 함께 요청받으면 재현·수정·재검증까지 진행할 수 있다.
- 기존 QA 브리지는 실제로 현재 빌드를 지원할 때 사용한다. 자동 에이전트나 팀 구성을 매번 요구하지 않는다.
- 결과에 근거·실패·미검증 범위를 함께 기록한다. 자동 성공 횟수를 UX 완성 점수로 바꾸지 않는다.
- 개편 검증에는 활성 프로젝트의 `docs/direction/development-workflow.md`를 사용해 요구/위험·시나리오·관련 코드/자산 상태·결과를 연결한다. 수정된 결함은 재현을 검출하는 기존 검사에 연결하고, 관련 변경 뒤 낡은 증거만 재확인한다. assert 수를 품질 기준으로 삼지 않는다.
- 모바일 후반 저하·발열·장시간 안정성 요청에는 `docs/qa/protocols/mobile-sustained.md`를 적용한다. 같은 기기의 초기/후반과 저장·복귀를 비교하고, 센서·기기·빌드가 없는 항목은 미측정으로 남긴다. PC 성능 검사나 절차 작성은 실기기 통과가 아니다.
- 사운드 검수는 실제 재생·동시 효과·음량 설정·장면 이탈까지 포함한다. 이벤트 로그만으로 청취 품질을 판정하지 않는다.
- APK 요청에서는 `docs/mobile-delivery.md`의 기존 절차를 재사용하고 테스트 목적에 맞는 증거만 요구한다. 새 실행 모드가 전달 도구에서 지원되는지 확인하며 내부 APK마다 정식 출시 체크리스트를 강요하지 않는다.
