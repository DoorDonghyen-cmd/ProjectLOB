# Project-Scoped Rules

## 리팩토링 진단 규칙 (Refactoring Diagnosis Rule)
- **트리거(Trigger):** 사용자가 "코드 리팩토링 필요할까?" (또는 유사한 뉘앙스)라고 질문할 때.
- **행동(Action):**
  1. **코드 상태 분석:** 즉시 현재 포커스 된 파일이나 관련된 주요 시스템 파일들의 상태(파일 크기, 줄 수, God Object 여부, 결합도, 단일 책임 원칙 위배 등)를 분석합니다. (예: `view_file` 또는 `grep_search`를 통한 구조 파악)
  2. **진단 보고:** 현재 코드가 리팩토링이 필요한 상태인지, 아니면 당분간 기능 구현에 집중해도 괜찮은 상태인지 객관적인 피드백을 제공합니다.
  3. **방향 제안:** 리팩토링이 필요하다면 어떤 모듈을 어떻게 쪼개는 것이 좋은지 구체적인 방향(예: UI 컴포넌트화, 로직 매니저 분리 등)과 현재 시점에서 진행할지 미룰지에 대한 '타이밍'을 함께 제안합니다.

## 작업 종료 자동 깃 서밋 규칙 (Session-End Auto Git Commit Rule)
> 이 규칙은 **[work.md](file:///d:/ProjectLoB/.agents/workflows/work.md) Phase 4 마무리 절차의 마지막 단계(4-5)**이다. 별도 병렬 절차가 아니라, 문서 갱신(4-1~4-4)을 마친 뒤 이어서 실행하는 종결 단계다.

- **트리거(Trigger):** 사용자가 "오늘 작업은 여기까지 할게", "작업 끝", "퇴근" 또는 유사하게 세션을 정리하겠다는 의사를 표현할 때.
- **행동(Action):**
  1. **선행 조건:** 반드시 work.md Phase 4-1~4-4(태스크 트래커·데일리 로그·히스토리·버그 트래커) 문서 갱신을 먼저 끝낸다. 그 변경분이 아래 커밋에 포함되어야 한다.
  2. **깃 상태 분석:** `git status`를 실행하여 작업 트리에 커밋되지 않은 변경 사항이 있는지 확인합니다.
  3. **자동 커밋:** 변경 사항이 있는 경우, 오늘 변경한 파일과 주요 수정 내역을 요약하여 직관적인 커밋 메시지를 자동 생성하고 커밋합니다. **커밋까지는 자동으로 수행합니다.**
  4. **푸시 승인 게이트:** `git push origin main` **직전에 푸시할 커밋 내역(파일 목록·커밋 메시지)을 유저에게 보고하고 승인을 1회 받은 뒤** 푸시합니다. (원격 main 직접 반영은 되돌리기 어려우므로 확인 게이트를 둡니다.)
  5. **결과 보고:** 업로드된 내역과 깃 링크를 보여주며 세션을 종료합니다.

## UI 개발 및 디버그 연동 규칙 (UI Development & Debug Rule)
- **트리거(Trigger):** 새로운 UI 화면 제작, 개편, 혹은 레이아웃 조율 작업이 감지될 때.
- **행동(Action):**
  1. **선 기획서 작성:** 소스 코드를 편집하기 전에 반드시 **UI 요청 제작 기획서 (예: `ui_request_*.md` 또는 `implementation_plan.md`)**를 세부 레이아웃 와이어프레임과 함께 작성하여 제출하고 사용자 승인을 먼저 획득해야 합니다.
  2. **디버그 숏컷 의무 제공:** UI 작업이 완료된 후, 메인 메뉴의 **`🛠️ 개발자 테스트`** 팝업 공간 내부에 즉시 해당 UI 화면을 호출하여 렌더링 결과와 데이터를 상호작용할 수 있는 숏컷(Shortcut) 버튼을 반드시 추가하고 연동 라우팅을 확보해야 합니다.

## 탄환 에셋 가공 및 연동 표준 규칙 (Bullet Asset Customization & Mapping Rule)
- **트리거(Trigger):** 새로운 탄환 그래픽 리소스를 제작, 가공, 또는 관련 리소스(.tres) 매핑을 진행할 때.
- **행동(Action):**
  1. **디자인 일관성 및 구도 확보**:
     - 모든 탄환 그래픽은 **우상단(1시 방향)을 향해 비스듬히 기울어진 사선 구성**을 엄격하게 준수하여 시각적 통일성을 이룹니다.
     - 한 탄종의 기본형(일반탄)이 결정되면, 특수탄 베리에이션은 새로 AI 이미지를 생성하지 않고 **기존 투명화 원본 파일에서 탄두 영역 색상 치환(Tinting) 기법**을 사용하여 아웃라인과 각도 등 형태적 일관성을 100% 보존합니다.
  2. **후처리 SOP 준수**:
     - **1차 (배경 제거)**: 이미지 모서리(0,0)의 색상을 기준 배경으로 삼아 플러드 필 배경 제거를 진행합니다.
     - **2차 (엣지 정리)**: 외곽 아웃라인 주변에 남는 흐릿한 안티앨리어싱 잔상 픽셀(밝은 회색/흰색)을 정밀 감지(Edge Cleaning)하여 완벽히 투명 처리합니다.
     - **3차 (리사이징)**: 픽셀이 뭉개지지 않도록 최근접 이웃(`NEAREST`) 필터 보간법을 사용하여 **128 x 128** 크기 파일로 변환합니다.
     - **4차 (아웃라인 보강)**: 전체 탄종의 픽셀 아트 스타일 일관성을 보장하기 위해, 가장자리 바깥 방향으로 **1px 두께의 선명한 검은색 아웃라인**을 덧칠합니다. *(참고: 캐릭터/크리처 스프라이트의 'no-outline' 원칙과 별개인 탄환 아이콘 전용 규격 — [08-art-resource-manager §3-5](file:///d:/ProjectLoB/.agents/skills/08-art-resource-manager/SKILL.md) 참조.)*
  3. **특수 효과별 표준 네온 색상 테이블**:
     - **일반탄 (Standard)**: 실버 / 메탈릭 그레이
     - **충격/넉백탄 (Knockback/Force)**: 일렉트릭 시안 (`#00DCFF`)
     - **슬로우/둔화탄 (Slow/Sticky/De-buff)**: 일렉트릭 블루 (`#0066FF`)
     - **견제/선제/경직탄 (Opening/Interrupt)**: 네온 오렌지 (`#FF4500`)
     - **리듬/콤보탄 (Rhythm/Combo)**: 네온 마젠타 (`#FF00FF`)
     - **치명/결전탄 (Critical/Gold)**: 일렉트릭 옐로우/골드 (`#FFD700`)
  4. **Godot 리소스 자동 바인딩**:
     - 가공 완료된 에셋은 `res://assets/sprites/bullet_[탄종_효과].png` 경로에 저장합니다.
     - 해당 탄환의 `.tres` 리소스 파일 헤더에 `[ext_resource type="Texture2D" path="..."]`를 등록하고 `icon` 프로퍼티에 할당하여 인게임 연동을 마칩니다.
